# Studio OS (שלב דמו)

המשרד האחורי ופורטל הלקוחות של סטודיו AMDIR: לידים, לקוחות, פרויקטים, משימות, אבני דרך, קבצים וגרסאות, הצעות מחיר.
**הכול כאן דמו.** כל הנתונים לדוגמה (`demo: true`), ושום ספק אמיתי לא מחובר: מיילים, תשלומים, חשבוניות והעלאות נרשמים ב"תיבת יוצאים" בתוך האפליקציה ולא נשלחים.

תיקייה עצמאית עם `package.json` משלה. לא נוגעת בבנייה של האתר הציבורי שבשורש.

## הרצה

צריך Node 22.22 ומעלה. כל הפקודות מתוך `os/`:

```bash
npm install
npm run dev         # http://127.0.0.1:4590
npm run typecheck   # tsc במצב strict
npm run lint        # ESLint (typescript-eslint + jsx-a11y), אפס אזהרות
npm test            # Vitest: לוגיקה, מאגרים, חוזי ספקים, מסכים
npm run build       # בנייה ל-os/dist
npm run e2e         # Playwright: זרימת עשן + axe על כל מסך (בהיר/כהה, 390/1440)
```

Playwright משתמש בכרום שב-`/opt/pw-browsers` אם קיים (כמו `scripts/qa.mjs` בשורש), או ב-`CHROME_PATH`. צילומי מסך נשמרים ב-`os/shots/`.

## מבנה

```
os/src/
  domain/      טיפוסים ולוגיקה טהורה, בלי React ובלי אחסון
  data/        ממשקי מאגרים (Repositories) + מימוש בזיכרון שנשמר ב-localStorage + זרע דמו
  providers/   ממשקי ספקים + מימושי דמו + חוזים (contract tests)
  app/         הרכבה: בחירת המימושים (bootstrap.ts), סשן מדומה, ניתוב, מעטפת
  features/    מסכים: dashboard, leads, clients, projects (לוח, פרויקט, הצעת מחיר), misc
  ui/          רכיבים בסיסיים בעבודת יד (כפתורים, תגיות, מצבי טעינה/ריק/שגיאה, שדות)
  styles/      tokens.css (מועתק מהאתר, כיוון "אינדקס") + app.css
```

הכלל: מסכים מדברים רק עם הממשקים (`Repositories`, `Providers`). החלפת מימוש קורית במקום אחד: `src/app/bootstrap.ts`.

### domain
- **כסף באגורות שלמות בלבד.** שום סכום לא נשמר כשבר עשרוני. כללי העיגול כתובים בראש `money.ts` ונבדקים:
  שורה = כמות × מחיר (עד 2 ספרות אחרי הנקודה, עיגול לאגורה); **מע״מ מחושב פעם אחת** על הסכום שאחרי ההנחה, לא לכל שורה;
  סה״כ = לפני מע״מ + מע״מ בדיוק. מע״מ 18% מ-1.1.2025 (טבלת שיעורים לפי תאריך). כל סכום ללקוח מוצג "כולל מע״מ".
- **שלבי פרויקט:** פנייה → הצעה → טרום הפקה → הפקה → פוסט → בבדיקת לקוח → נמסר → ארכיון.
  מעבר הוא צעד אחד קדימה או אחורה, או לארכיון; שחזור מהארכיון חוזר לשלב שממנו נשלח. אין דילוגים.
- **מספר הקצאה (חשבוניות ישראל):** חשבונית מס ללקוח עסקי בסכום של ₪5,000 ומעלה לפני מע״מ, מ-1.6.2026, צריכה מספר הקצאה.
  המערכת רק מסמנת את הדרישה (`invoicing.ts`); השגת המספר היא תפקיד ספק החשבוניות. **לאמת את טבלת הכללים מול רואה החשבון לפני עלייה לאוויר.**
- לידים: `lead.ts` קולט שורה של `public.studio_leads` (הטבלה של טופס האתר, `supabase/leads.sql`, אחרי ש-`server/lead/schema.ts` אימת אותה),
  בודק שוב את מה שהמערכת סומכת עליו, ומשמיט מפתחות brief לא מוכרים. המרה של ליד יוצרת לקוח (או מקשרת לקיים), פרויקט ואבן דרך ראשונה, בפעולה אחת.
- "מה מחכה לי היום" (`attention.ts`): לידים חדשים, הערות לקוח פתוחות, משימות באיחור, הצעות שאושרו ולא שולמו. הכול מחושב מהנתונים.

### data
- כל מתודה במאגרים אסינכרונית, כך שהמסכים כבר בנויים לרשת: טעינה, שגיאה עם "ניסיון נוסף", מצב ריק.
- המימוש בזיכרון נשמר ב-`localStorage` דרך עטיפה בטוחה (`storage.ts`): אם האחסון חסום או מלא, ממשיכים בזיכרון ומציגים אזהרה בפס הדמו.
- זרע הדמו (`seed.ts`) דטרמיניסטי: אותו יום → אותם נתונים, עם תאריכים יחסיים להיום. שמות בדויים בלבד ("לקוח לדוגמה א׳"), כתובות `.invalid`.
- כפתור "איפוס נתוני דמו" בפס העליון מוחק ומזריע מחדש.

### providers
`EmailProvider`, `StorageProvider` (קישורים חתומים בלבד, לא כתובות ציבוריות), `VideoHostProvider`, `PaymentProvider` (בלי ספק סליקה ספציפי), `InvoicingProvider`.
מימושי הדמו כותבים לתיבת היוצאים וכתובותיהם תחת `.invalid`, כך שאין דרך להגיע לשירות אמיתי.
`contracts.ts` מגדיר חבילת בדיקות לכל ממשק. **ספק אמיתי נכנס רק אחרי שעבר את אותה חבילה** (`describeEmailContract('resend', ...)` וכו').

## סשן ותפקידים
כניסה מדומה: בוחרים "בעלי הסטודיו" או "לקוח לדוגמה". לקוח רואה רק את `/portal` (כרגע עמוד שמור למקום, הפורטל הוא השלב הבא).
**אימות אמיתי יגיע עם Supabase Auth, והפרדת הנתונים תיאכף ב-RLS** (לקוח רואה רק שורות עם מזהה הלקוח שלו), לא רק בממשק.

## מה הלאה (לא בשלב הזה)
מימוש Supabase לממשקי המאגרים + RLS, פורטל לקוח (צפייה בגרסאות, הערות לפי קוד זמן, אישור הצעה ותשלום), ספקים אמיתיים לפי החלטת הבעלים.
